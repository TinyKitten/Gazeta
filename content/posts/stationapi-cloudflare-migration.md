**この記事はAIに丸投げしました**

きったんです。[TrainLCD](https://trainlcd.app/)の駅・路線情報や経路検索を支える[StationAPI](https://github.com/TrainLCD/StationAPI)を、Cloudflare Workersへ完全移行しました。

Rustで書いているAPIをWebAssemblyにコンパイルして、Workers上で動かしています。あわせてPostgreSQLもgRPCも、その手前にあったBFFもなくなりました。データベースを別のサービスへ引っ越したわけでもなく、検索に使うデータごとWASMに入っています。

今回は、どういう構成になったのかと、移行するときに何を確認したのかを書きます。

## もともとの構成

移行前は、自宅のRaspberry PiでRust製のStationAPIとPostgreSQLを動かしていました。アプリが呼ぶのはCloudflare Workers上のGraphQL BFFで、そこからgRPC-WebでStationAPIへ問い合わせる構成です。

つまり、入口はすでにCloudflareにあったものの、検索処理とデータは自宅にありました。

| 役割 | 移行前 | 移行後 |
| --- | --- | --- |
| アプリ向けAPI | Workers上のGraphQL BFF | Workers上のStationAPIがGraphQLを直接提供 |
| 検索・経路探索 | オンプレのRustサーバー | RustをコンパイルしたWASM |
| データの参照 | PostgreSQLへ問い合わせ | WASMに埋め込んだデータのインメモリ索引 |
| データの生成 | サーバー起動時にPostgreSQLへ取り込み | ビルド前にRustのツールで生成 |

StationAPIがGraphQLを直接返せれば、GraphQLとgRPC-Webを変換するBFFは不要になります。アプリが呼ぶURLと公開スキーマは引き継ぎ、裏側をWorkersにまとめました。[移行記録](https://github.com/TrainLCD/StationAPI/blob/ec7aed0031b98fcfa2d35455cb98883274419109/docs/cloudflare-workers-migration.md)に、変更前後の構成を残しています。

## データベースをなくせた理由

StationAPIが扱うのは、駅、路線、列車種別、停車駅の並びといったデータです。鉄道データの正本はリポジトリ内のCSVで、バスのデータはGTFSやODPTから取り込んでいます。APIは、それらをもとに検索結果を返します。

リクエストのたびにユーザーの情報を書き込むようなデータではないので、検索に必要な状態をあらかじめ作り、コードと一緒に配布できます。

そこで、データを`generated/*.csv`として生成し、ビルド時にWASMへ埋め込む形にしました。実行時には必要になったデータをパースして、駅IDや系統IDなどで引ける索引を作ります。索引は`OnceLock`に保持するので、同じisolate内でリクエストのたびにCSVを読み直す必要はありません。

ここでいうインメモリは、稼働中のプロセスにしかデータが残っていないという意味ではありません。元データはCSVや外部フィードにあり、配布するWASMにも埋め込まれています。実行環境が作り直されたら、そのWASMから索引を作り直します。[実装は`src/index.rs`](https://github.com/TrainLCD/StationAPI/blob/ec7aed0031b98fcfa2d35455cb98883274419109/src/index.rs)にあります。

D1やKVなどを新しい保存先として挟む必要もなくなりました。駅や経路を検索するリクエストは、外のデータベースへ通信せずに処理できます。

## Rustで書いていた処理を持っていく

既存のPostgreSQL接続やgRPCサーバーを、そのままWorkersへ持ち込んだわけではありません。SQLを実行していたリポジトリ実装をインメモリ版に差し替え、APIの配信部分は`async-graphql`で実装しました。

ここで役に立ったのが、データへのアクセスをrepositoryトレイトの向こう側に分けていたことです。経路探索や到着時刻の推定といった処理は、そのトレイトを通じてデータを取得していたので、既存のDomain / UseCase層を再利用できました。

最初のWorkers版を追加した段階では、約17,000行のDomain / UseCase層を変更せずに動かせています。ただし、その後の照合では既存の経路検索のパニックも見つけて修正したので、移行全体を通して一切変更していない、という話ではありません。[初期移植のPR](https://github.com/TrainLCD/StationAPI/pull/1635)と[旧構成を撤去したPR](https://github.com/TrainLCD/StationAPI/pull/1640)に、それぞれの変更を記録しています。

SQLでやっていたことも、用途に合わせてRustの処理に置き換えています。たとえば駅名の部分一致検索は、検索用の正規化を引き継いで`contains()`で比較します。旧実装では`pg_trgm`のGINインデックスで部分一致検索を高速化していました。今回使っていたのは類似度検索ではないので、文字列の部分一致として実装できます。

座標検索の距離計算はhaversineへ変更しました。移行時は全件走査で検証し、その後、現在の実装ではグリッド索引で近傍の候補を絞っています。データベースを外しても、検索の組み立て方や計算量を考える必要は引き続きあります。

## CSVを埋め込む前にも処理がある

ここは単に`include_str!`で既存のCSVを読めば終わり、とはいきませんでした。

旧構成では、CSVをPostgreSQLへ取り込む過程で、列車種別を持たない路線に各駅停車の系統を補っていました。この生成結果は、リポジトリにあるCSVには含まれていません。

移行時に確認したデータでは、この処理で2,427行が生成され、2,268駅に影響していました。元のCSVだけを埋め込むと、その分の情報が抜けたAPIになってしまいます。

まずはPostgreSQLへの取り込み後のデータをエクスポートしてWorkers版を検証し、その後、生成処理自体を純Rustの`preprocessor` crateへ移しました。現在のデータ更新は次の流れです。

1. リポジトリの鉄道CSVを読み、各駅停車の系統を補う。
2. GTFS・ODPTのバスデータを取得して統合する。
3. 事業者・路線・駅・種別・停車駅の対応・別名関連の7テーブルをCSVへ出力する。
4. `build.rs`でデータを配置し、停車駅の対応テーブルは固定長バイナリへ変換する。
5. WASMをビルドしてWorkersへデプロイする。

この変更で、PostgreSQLは本番だけでなく、ローカル開発とCIからも不要になりました。データ生成の実測は、旧構成の約7分半から6.3秒になっています。これは[移植時に記録した取り込み処理の値](https://github.com/TrainLCD/StationAPI/pull/1640)で、Rustのコンパイルやデプロイまで含めた時間ではありません。

## スキーマが同じでも、結果が同じとは限らない

GraphQLは、既存のBFFが公開していた18クエリ・28型に合わせました。公開スキーマを`schema/public.graphql`として保持し、Workerが生成するSDLとCIで比較しています。

たとえばenumの表記も互換性に関わります。`async-graphql`の既定の命名をそのまま使うと既存のスキーマとずれますし、PascalCaseへ変換しても`JR`が`Jr`になってしまうので、ここは名前を明示する必要がありました。

ただ、型が合っていても、返すデータが間違っていたらアプリは壊れます。そこで旧SQLの結果や、旧本番のGraphQLレスポンスと照合しました。移植時には、たとえば次のような問題が見つかっています。

| 見つかった問題 | 実際に起きること |
| --- | --- |
| 経路取得で列車種別を持つ停車駅の取得が抜けていた | 新宿→渋谷の経路が旧本番では20件、移植版では0件になる |
| 駅名検索で出発駅からの到達条件を適用していなかった | 乗り換えなしでは行けない駅まで候補に出る |
| 駅と路線を結ぶ処理で通過条件が抜けていた | その駅に停まらない路線が駅情報に混ざる |

これらは[移植側の実装を修正](https://github.com/TrainLCD/StationAPI/pull/1640)しました。停車駅については集合が一致するだけでは足りず、並び順も必要です。データ生成処理の比較では、2,587系統すべてで停車順が一致することを確認しています。

一方で、旧実装にそのまま合わせない差分もあります。座標の距離計算の変更や、もともとSQLで順序が確定していなかった箇所などです。何が不具合で、何が意図した変更なのかを分けて確認しました。

今回の移行では、WASMとしてビルドできたあとも、こうした検索結果の照合が必要でした。HTTPの成功やスキーマの一致だけでは、経路が0件になっていることまでは保証してくれません。

## データ更新もデプロイになる

データをWASMに埋め込むので、CSVを修正したり外部のバスデータが更新されたりしても、稼働中のWorkerへ自動で取り込まれるわけではありません。反映にはデータの再生成、ビルド、再デプロイが必要です。

現在はGitHub Actionsから、`dev`の変更をstagingへ、`master`の変更をproductionへ反映しています。生成処理をビルドの前に実行するので、駅名や停車駅の修正もこの経路で配布されます。

また、ビルドが成功したことと、必要なデータが揃っていることは別です。バスフィードの取得に失敗しても、前処理が警告だけで続行すると、バスデータの一部が抜けたWASMを作れてしまいます。デプロイ用の処理では、取り込めなかったフィードがあれば失敗させるようにしています。[ビルド処理](https://github.com/TrainLCD/StationAPI/blob/ec7aed0031b98fcfa2d35455cb98883274419109/.github/actions/build-worker/action.yml)と[本番デプロイ設定](https://github.com/TrainLCD/StationAPI/blob/ec7aed0031b98fcfa2d35455cb98883274419109/.github/workflows/deploy_production.yml)に、このチェックを入れています。

APIの切り替えでは、BFFが持っていたカスタムドメインをStationAPIへ移しました。ほかのWorkerからのService Bindingも付け替える必要があり、StationAPIの用意、呼び出し元の切り替え、BFFの削除という順序で進める作業です。[本番移行のissue](https://github.com/TrainLCD/StationAPI/issues/1638)に手順と対応完了の記録があります。

## 自宅のサーバーへ問い合わせなくてよくなった

今回の変更で、StationAPIの検索リクエストはCloudflare Workersの中で完結するようになりました。入口から自宅のAPIへ往復する通信も、その先のDB接続もありません。

応答時間にはネットワークやクエリの内容も影響するので、すべての検索が一律に何msになるという話にはできません。それでも、検索のために自宅の回線とサーバーへアクセスする構成をなくせたことは、運用上の大きな変化です。PostgreSQLの接続設定や、起動時のデータ取り込みを含むサーバープロセスの管理も不要になりました。

この作りが成立したのは、StationAPIが扱うデータをビルド時点でまとめられ、リクエスト中に更新する必要がなかったからです。その代わり、データをいつ取り込み直して配布するかは、デプロイの仕組みで扱います。

Rustで積み上げてきた検索処理を使いながら、配信もデータもWorkersへまとめられました。サーバーを引っ越すつもりが、データベースまでなくなりました。
